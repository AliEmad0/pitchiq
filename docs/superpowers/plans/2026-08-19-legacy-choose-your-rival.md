# Legacy Club — choose your rival

**Owner request, 2026-08-19.** "Add an option if the user wants to select the club he wants to
face — for example my team is Liverpool and I want to face Arsenal. Keep in mind: **not the other
team's players**."

Plus, on how that rival should be drafted:

> Ship a single static JSON per club holding their full available card pool (~20 KB). Every time a
> new match is generated against Arsenal, run an automated draft for them on the client: randomly
> pick a formation, generate their 11 + bench using the same draft logic the player has, selecting
> from Arsenal's card pool **randomly rather than strictly taking their top-rated cards**. This
> guarantees Arsenal feels fresh with different line-ups, formations and ratings (staying around the
> **82–90** range) every time you play them.

And on difficulty: **a choice on the setup screen.**

---

## What is true today

Both sides are drafted from the **same** club pool, which is why van Dijk marked van Dijk. As of
#177 the opponent drafts best-available and the coach's own XI is withheld from it, so the mirror
is gone — but the rival is still _your_ club's reserves, not another club.

## Measured, not assumed

`buildPool` over the committed data, three clubs:

| club           | cards | full JSON | distinct players | slim, all | slim, top 120 |
| -------------- | ----- | --------- | ---------------- | --------- | ------------- |
| Liverpool (40) | 873   | 640 KB    | 267              | 46.6 KB   | **20.8 KB**   |
| Man Utd (33)   | 933   | 688 KB    | 250              | 43.9 KB   | **21.1 KB**   |

"Slim" = one card per PLAYER (his best-rated season) carrying `cardId, playerId, season, name,
role, altRoles, ratings`. So the owner's "full pool at ~20 KB" is achievable exactly — as **the
club's best 120 distinct players**, which is far more than an XI plus bench will ever need.

Liverpool's rating distribution, by rank: 1–11 are 95→89, rank 30 is 84, rank 45 is 82, rank 60 is 78. **So "82–90" is the slice from about rank 8 to rank 45** — and a uniform draw over
`OVR >= 80` lands squarely inside it.

## The design

### 1. A rival file per club — `public/game/rivals/<teamId>.json`

Generated by `scripts/build-rival-pools.mjs`, committed, ~21 KB each, ~1.1 MB total on disk. Served
as a **static asset**, never an API route — no lambda, no Fluid Active CPU, and nothing added to any
page's payload. Only the club you actually pick is ever fetched.

⚠️ A test asserts each file matches what `buildPool` produces today, so the generator cannot drift
from the source of truth the pages use.

### 2. A third draft policy — `"strong"`

`DraftPolicy` becomes `"random" | "best" | "strong"`. `strong` is a **uniform draw among eligible
cards rated `STANDOUT_OVR` (80) or better**, falling back to the best available when a club has none
for that slot.

⭐ That is not a new rule — it is the _same_ rule the pack already applies to the coach's own hands
("one card at 80+, or failing that the best card the club can offer"). The opponent is drafted to
the standard the coach is guaranteed, which is exactly the fairness the owner is asking for, and it
produces a different XI every match because the draw is uniform inside the band.

The formation is drawn from `FORMATIONS` on the same seeded stream, so the rival's shape varies too.

### 3. A rival picker and a difficulty control on the setup screen

Both live in the shape bar, alongside "Lock in". The rival defaults to the coach's own club, so
doing nothing reproduces today's match. Difficulty is **Balanced** (`strong`, default) or **Best XI**
(`best`).

### 4. ⛔ The rival and the difficulty are part of the match's IDENTITY

This is the part that is easy to get wrong and expensive to get wrong. Resume and share both re-run
`buildSession` and verify by fingerprint — so a saved or shared match that does not carry the rival
club and the policy replays against a **different opponent** and presents as a corrupt save.

- `SavedMatch` gains `opponentTeamId` + `policy`.
- `ShareableMatch` gains them too, which means the codec goes **`v1` → `v2`**. A `v1` code is
  refused rather than replayed into a plausibly-different match — the rule the token stream already
  follows.
- The rival's cards must be resolvable by the RECEIVER, so the share link carries the rival id and
  the receiving page fetches that rival file before replaying.

## Build order

| 1   | The generator, the 51 committed files, and the sync test       | Data before UI; nothing else can be built without it  |
| 2   | `"strong"` policy + rival-pool plumbing through `buildSession` | Pure domain, fully unit-testable, no UI               |

## Open risks

- **A rival's best 120 is not his full history.** A future mode that wants to draft the rival's
  whole 900-card pool cannot use these files. That is a deliberate trade for the ~20 KB the owner
  asked for; the club-in-the-URL page still carries the complete set for the coach's own side.
- **The card face.** The pre-match programme renders "THEIR XI" as full FUT cards, which want
  `photo`, `age`, `nationality`. Those fields must be measured into the slim card before PR 1 ships
  — if they push a file past ~35 KB, the cap drops from 120 to the top 80, which is still far more
  than a squad needs.
